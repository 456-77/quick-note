M0 的目标是验证外壳可行性：能用 Tauri v2 + CodeMirror 6 做一个打开目录、编辑、保存
都在字节层面无损的最小笔记软件，并现场测出内存基线。

## 核心约束：为什么必须字节精确

同步协议用内容的 **SHA-256** 判断增量（见 `daily-sync` 的 `sync.ts` 与后端
`SyncService`）。它对每个文件存一份 `content_hash`，哈希一致就跳过、不一致就当成改动，
冲突时本地胜出并回推。这意味着：

> 只要读写链路对未改动的文件产生任何字节差异，同步就会把它判成"已改动"。

后果不是数据损坏，而是**每个文件在每次同步时都被重传、并可能触发虚假冲突提示**。
CRLF 是最容易踩的雷：Windows 上大量 Markdown 文件是 CRLF，而几乎所有编辑器库默认
按 LF 处理字符串。

## 实测发现的两个 CodeMirror 6 陷阱

这两个都是先写出错误实现、再被验证脚本抓出来的，不是推测。

### 陷阱 1：`state.doc.toString()` 不遵守 `lineSeparator`

官方文档说配置 `lineSeparator` 后"可以往返而不规范化换行符"，但**只有 `sliceDoc()` 遵守**。
实测（`lineSeparator = "\r\n"`，内容为 CRLF）：

| API | CRLF 文件往返是否精确 |
|---|---|
| `state.sliceDoc()` | ✅ 一致 |
| `state.doc.toString()` | ❌ 被改写成 LF |

`doc.toString()` 固定用 `\n` 拼接。所以序列化必须走 `sliceDoc()`。

### 陷阱 2：`lineSeparator` 是 facet，切换文件必须重建状态

facet 在状态创建时就确定了行切分与 `lineBreak`。切换文件时若复用旧状态，新文件会沿用
上一个文件的换行符风格。M0 的做法是每次打开文件都 `view.setState(createEditorState(...))`。

顺带确认：`insertNewline`（`@codemirror/commands` 内部用 `state.lineBreak`）会插入正确的
分隔符，所以在 CRLF 文件里按回车不会混进 LF。

## 验证策略，以及一次假阳性

完整的字节精确链路被拆成两段分别验证，都不需要启动 GUI：

1. **磁盘 ↔ 字符串**（Rust 集成测试）：读出来原样写回，字节必须一致且 mtime 不变；
   编辑后再恢复原文，字节必须回到初始值。
2. **字符串 ↔ 编辑器状态**（Node 脚本）：`sliceDoc()` 必须与输入字符串完全一致。

测试仓库覆盖：LF、CRLF、仅 CR、混合换行、无尾随换行、空文件、UTF-8 BOM、中文、
GFM 表格/任务列表/围栏代码/原始 HTML、嵌套目录，以及应被跳过的隐藏文件与非 md 文件。

**假阳性教训（重要）**：第一版测试脚本自己复刻了一份换行符探测逻辑，其中的比较条件写错，
把 CRLF 文件判成 LF。测试却"通过"了——因为用 `\n` 分隔符解析 CRLF 内容时，`\r` 会留在
行尾作为普通字符，`sliceDoc()` 恰好也能还原原始字节。**CRLF 分隔符那条代码路径从未被真正
执行过，测试却给了绿灯。**

修正方式不是把复刻逻辑改对，而是**取消复刻**：由 Rust 通过
`src-tauri/examples/dump-detect.rs` 导出探测结果作为唯一地面真值，脚本直接消费。
同时补了两条断言堵住这类漏洞：

- 断言 `state.lineBreak === 期望分隔符`，确认 facet 真的生效，而不是碰巧通过；
- 对 CRLF 文件断言没有任何一行以 `\r` 结尾，确认行切分正确。

推广原则：**同一个判定不要写两遍**。测试若与被测代码共享同一份真值来源，就不会出现
两边一起错还能通过的情况。

## 内存实测（本机，2026-09-14）

测量条件：release 构建，已打开一篇笔记，启动后约 30 秒。命令
`powershell -ExecutionPolicy Bypass -File scripts/measure-rss.ps1`。

### 三个指标给出互相矛盾的结论

| 指标 | Quick Note | Obsidian | 谁更省 |
|---|---|---|---|
| 工作集合计 (WorkingSet) | 408.3 MB | 211.1 MB | **Obsidian** |
| 私有提交合计 (PrivateBytes) | 148.5 MB | 696.9 MB | **Quick Note（4.7×）** |
| **私有工作集合计 (PrivateWS)** | **99.5 MB** | **145.9 MB** | **Quick Note（约省 32%）** |

三个数字都不能直接当结论用，原因在口径：

- **WorkingSet 重复计算共享页**。Quick Note 有 7 个进程，WebView2 的 DLL 与 Edge 及
  自身各进程共享，每个进程都各算一遍，于是 408MB 里很大一部分是重复的。这解释了
  为什么"更轻"的应用反而在工作集口径下更大。**这个口径不适合作跨应用对比。**
- **PrivateBytes 包含已换出到页面文件的部分**。Obsidian 已运行较久，提交量 697MB，
  但其中大部分并不占物理内存——所以它的工作集反而只有 211MB。
- **PrivateWS（私有工作集）** 只统计物理内存中真正属于该应用且不共享的部分，
  是三者中最接近"实际吃掉多少内存"的口径。

### 诚实的结论

- 按最公平的口径，Quick Note 约 **99.5MB**，Obsidian 约 **145.9MB**，**大约省 32%**。
- 这**远小于** 697MB/148MB 暗示的 4.7 倍。本文档第二节曾预估目标为"从 400MB~1GB+
  降到 100~200MB"——实测说明 Obsidian 在本机的物理占用只有约 146MB，我此前引用的
  量级偏高了。**Quick Note 落在预估区间的较好一端，但相对 Obsidian 的优势是约三分之一，
  不是数倍。**
- 这是一次**非受控对比**：Quick Note 是刚启动、只打开一篇小笔记；Obsidian 已运行较久、
  注册了 3 个仓库、带插件。要得出可靠结论，应在**两者都冷启动、打开同样的笔记**后再测。
  如果 Obsidian 在大仓库 + 大量插件下的物理占用显著上升，本项目的相对优势才会更大——
  这一点需要你用自己的真实仓库验证。

### Rust 主进程只占 5.5MB —— 印证了选型判断

进程树明细（GPU 关闭时）：Rust 主进程私有内存仅 5.5MB，其余全部来自 6 个 WebView2
进程（浏览器进程 69MB、渲染进程 37MB、两个工具进程、GPU 进程、crashpad）。

这正是第二节那句判断的实测印证：**外壳只决定地板，地板由 Chromium 内核决定；省内存
要靠架构**（单 webview、不把全库索引放进渲染进程、重依赖懒加载）。M0 已确认
CodeMirror 的语言包会自动切成独立 chunk 按需加载。

### 关掉 GPU 进程：私有内存 −33%

文本编辑器用不到 GPU 加速，实测关掉后收益明显：

| WebView2 参数 | 私有提交 | 私有工作集 |
|---|---|---|
| 默认 | 220.4 MB | — |
| 仅 `--disable-gpu-compositing` | 193.8 MB | — |
| **`--disable-gpu --disable-gpu-compositing`** | **148.5 MB** | **99.5 MB** |

已在 `src-tauri/src/lib.rs` 的 `WEBVIEW2_ARGS` 里默认开启。代价是走软件渲染，重绘更吃
CPU；若更在意滚动流畅度，删掉这两个开关即可。

> 实现细节：这里是**在 Rust 里拼接环境变量**，而不是写进 `tauri.conf.json` 的
> `additionalBrowserArgs`。因为配置里的值会**覆盖** `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`，
> 那样 `scripts/gui-*.mjs` 就无法再注入 `--remote-debugging-port` 做端到端测试。拼接可以
> 让默认优化与测试注入共存——已实测两者同时生效。

## 待办与遗留风险

- **换行符规范化的互通性（M3，需优先验证）**：本项目的哈希基于**原始文件字节**（含 BOM）。
  Obsidian 插件侧的 `sync.ts` 是通过 Obsidian 的 vault API 读文本再哈希的，其内部是否
  剥离 BOM、是否把 CRLF 规范化成 LF **尚未核实**。若两边口径不一致，CRLF 文件会被双方
  反复判成"已改动"，产生持续的虚假冲突。M3 动工前必须先对齐这一点。
- **文件监听缺失**：外部（Obsidian、同步、其他编辑器）改动文件时界面不会刷新，且可能在
  保存时覆盖外部改动。M1 需接入 `notify` 并加冲突提示。
- **切换文件时的保存竞态**：目前切换前会先保存，但如果保存失败仍会继续打开新文件，
  旧文件的改动可能只留在内存里。M1 需要把失败路径做成显式阻断。
- **尚无搜索/索引/日历**：M2/M3 内容，届时引入 SQLite（FTS5）作为可重建缓存。
- **内存基线未测**：需要首次构建出二进制后运行 `scripts/measure-rss.ps1`，与日常使用
  Obsidian 的实测值对比。
- **`.md` 之外的文件**：目前只列举 `.md`。插件的附件目录、`quick-daily-note.json`、
  `daily-sync-todos.json` 都还需要访问能力（`.json` 在协议里是合法的同步路径）。

## 过程教训

- **`create-tauri-app --force` 会清空目标目录**。本次在已有 `docs/` 的目录上跑脚手架，
  先前写好的选型文档被删除（已重新补写）。**在非空目录上脚手架前必须先备份。**
- **不要把后台命令的输出管道给 `tail`**。管道会缓冲全部输出，导致长时间看不到进度；
  更要紧的是退出码变成 `tail` 的，本次因此把一次**编译失败**误读成成功
  （真实原因是 rustc 版本过低）。后台任务应直接输出到日志文件。
- **不要用 `cargo build --release` 代替 `tauri build`**。绕过 Tauri CLI 时 `tauri-build`
  拿不到生产模式标志，产出的二进制仍然指向 `devUrl`（`http://localhost:1420`）。在没有
  Vite 开发服务器的情况下它就是一个**白屏的"假 release"包**——而对着白屏测出的内存数字
  完全无效（本次先测到 204MB，是白屏的空壳值）。正确做法是
  `npm run tauri build -- --no-bundle`（`--no-bundle` 跳过安装包，只出二进制）。
- **Windows PowerShell 5.1 按 GBK 读取无 BOM 的 `.ps1`**，中文注释会被解码成乱码并导致
  语法错误。含非 ASCII 的 PowerShell 脚本必须存为 **UTF-8 with BOM**。
