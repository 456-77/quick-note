## 一、云同步端到端联调（模拟器 ↔ 宿主桩后端）

`scripts/gui-android-sync.mjs`：**Android 版同步冒烟**，对裁剪自桌面 gui-sync 的
桩后端（login/refresh/POST 推送/GET 拉取，端点形状逐字节一致）跑完整往返。

- **网络拓扑**：桩后端绑宿主 `127.0.0.1:9299`，应用（模拟器）配置
  `http://10.0.2.2:9299`——Android 模拟器把 `10.0.2.2` 映射到宿主 loopback。
  走 http，验证的是**通道与接线**；rustls+WebPki 的 https 归真机对正式服务器验证
  （net.rs 的 TLS provider 已有 `#[ignore]` 测试守护 provider 指认）。
- **断言清单（15 项，全绿）**：设置面板配置生效进就绪 → 首推（6 个文件）→
  **CRLF 字节原样上云** → 状态文件在应用私有配置目录而**不在共享存储仓库里**
  （含密码令牌）→ 云端注入新笔记 → 点状态栏立即同步 → **拉取落盘内容完整** →
  所有同步请求携带令牌且被接受。
- **一个正确行为澄清**：reload 后应用直接复用状态文件里持久化的 accessToken/refreshToken，
  不重新登录——桩后端重启（不认识旧令牌）时走 401 → 刷新 → 重新登录的自愈链路，
  与桌面语义一致。

### 联调环境踩坑记录（复现时省时间）

1. **`MANAGE_EXTERNAL_STORAGE` 的授予必须以应用主进程实测为准**：
   - `adb shell appops set <pkg> MANAGE_EXTERNAL_STORAGE allow` **不够**——它是
     package 级 op，FUSE 检查的是 **UID 级**（`appops set --uid <pkg> ... allow`）；
   - 设置了也可能被 **run-as 代理进程**否决——run-as 的 cat 被拒**不代表**应用没权限
     （run-as 进程不携带 app 的 storage 身份）；
   - 唯一可信判据是**应用内真实读**（`read_note`）。模拟器上也可用
     `am start -a android.settings.MANAGE_APP_ALL_FILES_ACCESS_PERMISSION -d package:<pkg>`
     打开系统开关页自动化点授（本机最终状态：UID+package 双 allow，应用读正常）。
2. **`adb shell` 写共享存储**（预置测试文件）：文件名带空格必须
   `execFileSync("adb", ["shell", 整条命令])`；Git Bash 会把 `/sdcard/...` 转成本地
   路径，必须 `MSYS_NO_PATHCONV=1`。
3. **CDP `Runtime.evaluate` + `returnByValue`**：`document.querySelector(...)` 返回
   DOM 节点会报 `Object reference chain is too long`——查询断言一律写 `!!expr`；
   `app_data_paths` 的返回对象序列化同样会炸，改用 `run-as find` 定位文件。
4. **stub 残留进程**：脚本异常退出会跳过 `server.close()`，Windows 上多个 Node
   进程可绑同一端口（SO_REUSEADDR 语义），请求随机分发——症状是"POST 到了但状态没写"。
   重跑前确认 9299 无 LISTENING。
5. `Page.reload` 后应用在 vault 内，`.brand`/`.create-row` 等选择器与桌面一致。

## 二、回前台重扫（基础目录模型的必需要求）

固定私有仓库时代「无外部改动源」的假设**已失效**：仓库现在在共享存储，电脑 USB
拷贝、网盘/Syncthing 都可能改文件。`watch.rs` 的 notify 在 Android 上对 FUSE
的 inotify 支持不完整（子目录事件经常丢失），因此：

- `App.tsx` 新增 `visibilitychange` 监听（仅移动端）：`visible` 时对当前仓库
  `refresh(dir)` 整目录刷新。WebView 的 visibilitychange 在 Activity onResume
  时触发，无需任何原生代码；
- 桌面路径完全不受影响（`isMobile()` 短路）；
- 改动较多的大仓库刷新成本：一次 `list_entries` 深度遍历，实测 60 篇笔记仓库
  毫秒级，可接受；后续可做 mtime 对比增量。

## 三、设置面板「存储」分区集成

- 新 prop：`vaultHome`（基础目录路径）与 `onOpenVaultPage`（关闭设置、弹仓库列表页）；
- 移动端在「数据与缓存位置」上方渲染**仓库基础目录**卡片（路径 + 「打开仓库列表…」）；
  桌面端查询结果为 null，区块不渲染，零影响；
- 换基础目录仍在仓库列表页的「更改基础目录」操作（那里有完整的 SAF 流程与错误提示），
  设置页只读展示——避免两处入口状态不同步。

## 四、附件导入的现状与去向

- **已有通道够用**：桌面端粘贴/裁剪的图片经**附件云同步**（M3 已实现，按引用扫描、
  白名单、10MB 上限）自动落到手机仓库——本篇的同步联调就是它的通道验证；
- **SAF 相册直接导入**：Android WebView 的 `<input type=file>` 需要 Activity 实现
  `onShowFileChooser`（Tauri 的默认 MainActivity 没有），纯前端方案不成立；
  自定义 Activity/插件属原生开发，排 **A2/A3**（与系统分享接入同一批原生工作）。
  决策记录：不为附件导入提前引入原生插件。

## 五、验证

- `cargo test`（含 vault_home 2 项）✅；`tsc` ✅；桌面 `verify-all.sh` 12 步 ✅
  （visibilitychange 与设置改动不影响桌面路径）；
- `node scripts/gui-android-sync.mjs` 全绿（§1 断言清单，SYNC_OK）；
- 回前台重扫：`adb shell input keyevent KEYCODE_HOME` 退后台 → `adb shell sh -c

  验证路径；visibilitychange 的自动触发在 A2 移动 UI 验收里加 GUI 断言）。
