# M3 实现说明：云同步

M3 把 Quick Note 接到已有的 daily-sync 服务上，与 Obsidian 插件（`quick-daily-note`）
**共用同一个云端仓库**：同一批笔记、同一份待办、同一套游标语义。两边可以换着用，
也可以同时开着。

与 M2 一样，这一轮的核心约束来自"两边共用一份数据"：任何协议细节分叉，最轻的表现是
两边互相把对方推的变更再推一遍，最重的是**一边把另一边的数据删掉**。所以下面记的重点
不是"实现了什么"，而是**为什么是这个口径、以及哪些地方刻意与插件保持一致或刻意不一致**。

## 一、开工前的阻断项：内容哈希的口径

`docs/技术选型.md` 把这一条列为"M3 阻断项，优先级最高"：

> 本项目的哈希基于**原始文件字节**（含 BOM），而插件是经 vault API 读成文本再哈希的——
> 它是否剥离 BOM、是否把 CRLF 规范化成 LF 尚未核实。若两侧口径不一致，所有 CRLF 文件
> 会被双方反复判定为"已改动"，产生持续性虚假冲突。

### 核实结果（不再是"尚未核实"）

Obsidian 的实现可以直接读——`resources/obsidian.asar` 里有它的 `Vault.prototype.read`：

```js
// Vault.prototype.read：先经 adapter 读文本，再剥掉开头的 U+FEFF（65279）
t = (await this.adapter.read(e.path));  // adapter.read = fs.promises.readFile(path, "utf8")
65279 === t.charCodeAt(0) && (t = t.substring(1));
```

结论：**剥 BOM，换行符不做任何规范化**。于是本项目采用的同步口径是：

> **同步哈希 = 已剥离 BOM 的正文，按 UTF-8 字节求 SHA-256。**

三种行尾（LF / CRLF / 单独 CR）、尾随换行、混合行尾**原样参与哈希**——因为两侧都不动它们。

### 交叉验证

插件自己的 `data.json` 里存着它同步过的每个文件的内容哈希，那是"Obsidian 亲口说的真值"。
用它库里 9 个文件逐条比对：按"剥 BOM 后哈希"算出来的值与插件存下的**逐条相同**；
这 9 个文件恰好都不带 BOM，所以"按原始字节哈希"也相同——两组值一致，说明差异确实只
出现在带 BOM 的文件上，而那正是需要选边的地方。

待办快照（`daily-sync-todos.json`）的那个哈希**复现不出来**：快照里的条目 id 是
`crypto.randomUUID()` 生成的，迁移时产生的那批 id 没有留在磁盘上，任何离线复算都拿不到
同一串字节。这不是缺口而是这类哈希的性质——快照格式因此直接照抄插件与网页端的读写实现。

### 一个必须同时成立的性质

**BOM 不进哈希，但也不从文件里删掉。** 写回仍然是字节精确的（M0 的硬约束没变）：

- 读取时剥掉 BOM 再哈希（对齐 Obsidian）；
- 推送的内容是不带 BOM 的正文（BOM 也不该上云）；
- 磁盘上的 BOM 原样保留——`read_note` 多返回一个 `syncSha256` 字段专门给同步用，
  原有那个"原始字节哈希"继续服务于界面显示与"这个事件是不是我自己写的"。
- 采纳远端内容时（`adopt-remote`）**保留本地文件原有的 BOM**。这里与 Obsidian 有一点
  不同：它的 `vault.modify()` 会把 BOM 写没。保留更不具破坏性，而且对同步毫无影响
  （BOM 不参与哈希）。

## 二、分工：什么放在 Rust，什么放在 TS

| 位置 | 内容 | 为什么 |
|---|---|---|
| Rust `net.rs` | 一次 HTTP 请求（字节进、字节出、状态码原样回） | 渲染进程的 `fetch` 受同源策略约束：后端没有 CORS 响应头，WebView 的源（`tauri.localhost`）发不出去。而且同步要带账号密码与 JWT，不该放在页面脚本能直接读到的地方 |
| Rust `vault::sync_scan` | 遍历范围内的笔记、算同步哈希 | 一次 IPC 拿回整张表；逐个文件来回 IPC 在大仓库上会明显拖慢一轮同步 |
| TS `sync.ts` | 状态形状、范围判定、**冲突决策**、URL 与仓库名归一化（**纯函数**） | 冲突策略是唯一会丢数据的部分，做成纯函数才能在 Node 里把每个分支断言到 |
| TS `syncEngine.ts` | 一轮同步的编排（扫描 → 拉取应用 → 推送）、鉴权与续期 | 它只做"读盘/写盘/发请求"，判断都委托给 `sync.ts` |
| Rust `sync_store.rs` | 同步状态的存取（不透明文本） | 状态里有密码与 refreshToken，必须是设备本地文件；Rust 只负责原子写，不理解字段 |

`net.rs` 刻意**不解释业务状态码**：401 要不要续期、404 是不是"云端没有这个附件"，
都是同步逻辑的事，放在能被单测覆盖的那一层比埋进一个不透明的封装里清楚。

## 三、一轮同步做什么

```
scanLocalFiles   本地与上次同步的哈希差异 → 待推送队列
                  本地删掉的文件（哈希表里有、磁盘上没有）→ 墓碑
pullAndApply     GET /api/v1/sync?vault=&since=&limit=500 按版本号增量拉取
                  按 path 去重取最新；应用时按冲突策略决定采纳/保留/删除/重建
doFlush          POST /api/v1/sync?vault= 分批推送（≤200 条/批）
```

几个容易做错的地方：

- **游标是仓库版本号，不是时间戳**，`hasMore` 时下一页的 `since` 取"末条 version − 1"
  并回退一个版本让同版本组整组重取，客户端按 path 去重（重复是预期行为）。
- **游标要把附件元数据的版本号一起算进来**。附件本轮不下载，但它与正文**共用同一条
  版本计数器**：只看正文的话，游标会卡在一堆附件版本号之前，同一页每轮都被重新拉取、
  `hasMore` 永远为真。这一条在 GUI 测试里有一条专门的断言。
- **自己写入产生的回声不需要特殊标记**。插件的文件事件是同步回调，所以它需要一个
  `applyingRemote` 计数器把自己造成的写入挡掉；我们的事件经过 notify 与 250ms 去抖，
  早就错过了那个窗口，靠内容哈希判定反而更可靠（M1 处理"自己写入的回声"用的就是同一招）。
- 推送前逐条比对内容哈希，一致就不发请求。服务端本身也幂等（同路径同内容回 `unchanged`
  且不推进版本号），客户端这层只是省一次注定为空的请求。

## 四、冲突策略

只用三个哈希判断：**上次同步时的**（`knownHash`）、**本地的**、**远端的**。

| 情况 | 处理 |
|---|---|
| 本地 == 远端 | 什么都不做，记下哈希 |
| 本地 == 上次同步值（本地没动过）、云端改过 | 采纳云端（`adopt-remote`） |
| 双边都改过 | **本地胜**：保留本地并重新推送（`keep-local`），界面列出冲突文件 |
| 云端墓碑、本地没动过 | 跟随删除（进仓库内 `.trash`，可找回） |
| 云端墓碑、本地改过 | 本地胜：复活并重新推送（`resurrect-local`） |
| 本地文件已不在、而上一次同步的正是远端这份 | 补一个墓碑（`push-delete`） |
| 云端新增、本地没有 | 在本地重建（`create-local`） |

用"本地 == 上次同步值"而不是比对修改时间：**时间戳跨设备不可比**（时钟偏差、时区、
夏令时），而哈希是内容本身的指纹。

### 与插件的唯一差别：`knownHash` 未知且本地有文件时，本地胜

插件把这个情况当成"本地没动过"，直接用云端内容覆盖本地。它假设"本设备不认识这个文件
= 这个文件不是我的改动"。在我们这里有个高概率场景会踩中它：**同步状态损坏后点
「重置同步状态」**（哈希全清）。那一刻每个本地文件都变成"不认识"，云端内容会成片覆盖
本地——**把一次读取失败放大成一次全库回滚**。

反过来（本地胜）不会死循环：本地内容先推上去，对方的 `knownHash` 等于它自己的旧内容，
于是对方采纳我们的版本，两侧收敛。代价是"两边都改过又都失忆"时由本地赢。

这条差异的副作用要说清楚：**首次同步时，本地与云端不一致的文件以本地版本为准**。
同仓库两边都在用、又都不是首次同步时，行为与插件完全一致。

## 五、本地删除怎么传播（以及一个差点删掉云端整个目录的坑）

插件的删除事件能直接告诉它"这个文件被删了"，我们的文件监听只报路径、不报操作类型。
所以删除靠**扫描时的对比**发现：哈希表里有、磁盘上没有 → 推墓碑。少了这一步，
本地删除永远同步不出去。

问题是"上次同步过、这次不在扫描结果里"有**两种**成因，必须分开：

- **文件真的没了**（应用里删的、资源管理器里删的、改名了）→ 推墓碑；
- **只是离开了推送范围**（用户把日记目录从「日记」改到「日记/新」）→ **什么都不做**。

第一版的清理逻辑没有区分，于是**改一次日记目录就会把云端上旧目录的笔记全部打成墓碑**
——正是插件注释里记着的那次事故（游标/哈希错位导致"全部文件被判成本地离线删除"）。
修法是问一次完整文件表（`list_entries`，含范围外的文件）来区分"不在范围"与"不存在"。
写这条的用例时发现的，现在有一条断言专门守着它。

## 六、待办：虚拟文件与条目级合并

待办与插件一样走**虚拟文件**：内容只在内存里参与同步，不往用户库里落任何文件。

- 为什么不同步库内的 `quick-daily-note.json`：那份文件除了待办还混着 `emailAccessKey`
  等配置，整份上传等于把凭据送到服务端、再经接口回到浏览器。只取 `todos` 一个字段。
- **快照内容必须稳定**：`updatedAt` 用「待办最后一次修改时间」而不是当前时间。每轮都刷成
  `Date.now()` 会让快照哈希每轮都变——本机不停推送，并把别的设备更新的数据压掉。
  这条是插件踩过之后的结论，M2 已经为此把 `todosUpdatedAt` 单独留在配置里。
- **合并按 `id` 条目级对齐**：两侧都有取 `updatedAt` 更新的一侧（含它的日期归属与删除
  标记）；只有一侧有就保留；墓碑不进结果；同一天内按 `updatedAt` 升序保证两侧顺序一致。
  一边加一条、另一边勾一条不会互相冲掉。
- **合并改了本地就回推**（`changed`），让第三台设备也拿到合并结果。
- 显式区分"用户改待办"与"云端快照并进本地"：前者要主动通知同步引擎（待办不落盘、
  没有文件事件，靠 `onTodosChanged`），后者由同步引擎自己按 `changed` 决定。**新设备
  首次同步时绝不能在加载时推一次快照**——那时本地还没有云端那份数据，推上去就是把
  云端的待办覆盖成空的。

## 七、状态与凭据放哪

同步状态（服务端地址、账号、密码、refreshToken、游标、各文件哈希）存在
**应用配置目录的 `sync-state.json`**，不进仓库、不进 localStorage：

- 进仓库会被同步出去、也能被别的设备覆盖（插件为"新设备把全部文件误判成离线删除"踩过一次）；
- 进 localStorage 会被 WebView 数据目录的清理一起抹掉，那时每篇笔记都会被判成
  "本地改过"，撞成一片冲突。

**状态文件读不出来或解析不出来时不静默降级**：直接暂停同步并挂横幅说明。按默认值继续
会把游标归零当成"全新设备"，把本地文件全推一遍——把一次读取失败放大成全库覆盖。
横幅给两个出口：**重新读取**（可能只是暂时读不到）与**重置同步状态**（用户知情地从头开始）。

**写不进去则只警告、不停同步**（盘满、权限）。两者的处理刻意不同：读失败时我们**不知道**
自己上次看到过什么，继续同步是危险的；写失败时游标与哈希还在内存里，这一轮同步完全有效，
代价只是"重启后退回上次落盘的状态"——那是多拉一次的代价，比"写到一半就不动了"轻得多。

## 八、这一轮踩到的两个坑

**配置改动静默丢失。** 改一个设置项会顺带"重读一次状态文件"（为了让新范围、新仓库名
生效），而落盘是 300ms 防抖的——重读把刚填的地址与账号又读回成空。界面上表现为
"开关点了没反应，点同步说请先填写服务端地址"。修法是把两个动作拆成两个计数器：
`reloadToken` 只管从磁盘重读，`engineToken` 只管重建引擎（不动内存状态）。

**测试脚本里"打标记再查标记"会命中最旧的元素。** GUI 测试的第一版给要填的输入框打上
`data-test-target`，然后 `querySelector('[data-test-target]')` 去取——标记留在 DOM 上，
第二次查询命中的是**第一个**被打过标记的输入框，于是所有值都灌进了「服务端地址」，
看起来像同步配置根本没生效。现在改成"查找、赋值、派发事件在同一个 evaluate 里完成"。
这类失败很值得记：**它看起来是产品 bug，其实是测试自己在说谎**。

### 为什么界面层用**桩后端**

验收必须在没有网络、没有 Docker 的机器上跑得完（`verify-all.sh` 的既有约定）。而且这里
要验证的恰恰是"字节怎么进怎么出""401/404 不被当成网络故障""`hasMore` 分页与游标"这些
边界——桩比真服务器更容易构造，也更容易断言请求本身（比如"游标推进到了附件版本号"）。

代价是：桩的**协议实现**也要对（分页规则、幂等语义）。它只实现本项目用到的那几个接口，
所以真后端的行为差异（限流、配额、附件接口）不在这一层的覆盖范围内。

### 两个测试写法上的决定

**不自己算日期。** 待办回流那条要往"当前选中的那一天"注入数据，日期从 DOM 的
`data-date` 读——面板只渲染选中日的待办，自己算日期会在跨零点、跨月时静默错位。

**不从 DOM 的状态推断业务结论。** 冲突、凭据错误这些都断言界面上真的显示了对应文案，
而不是"我觉得它应该报了错"。

## 十、附件同步（M3 补全）

正文同步落地后，附件按插件同一套策略补齐，两条通道：

- **上传：按引用扫，不按目录扫**（Rust `sync_scan_attachments`）。粘贴图片的落点取决于
  用户配置，盯目录必然漏；按引用扫与落点无关，没被引用的图片不上云——不镜像无用的
  二进制。名字 → 路径的解析（同目录优先 → 最短路径 → 字典序）在 Rust 侧完成，**必须**
  与服务端 `AttachmentService.resolveByName` 同一套顺序：两边解析不一致的话，取回的图会
  落到不同路径，下一轮扫描把它当成另一个附件重复上传，云端多出一份。
- **下载：本地缺的图按文件名去云端补**。本地没有这个文件时引用是解析不到的，所以
  "本地缺图"恰好只会表现为"引用得到名字、找不到文件"。服务端用 `X-Attachment-Path`
  回真实路径，**必须落到那个路径上**——没有这个头宁可不下，凭空造路径等于制造重复附件。
- 已上传过的附件靠 mtime+size 的旁路缓存（stamp）跳过重读；哈希一致就不发请求，
  服务端对同路径同内容回 unchanged 且不推进版本号。
- 每轮下载有额度（20 个 / 50MB），被推迟的下一轮由引用重新推导出来继续，不会漏。
- 同步过、但现在既没被引用、本地也没了的附件推墓碑；**只删引用、文件还留着的不推**——
  云端那份留着更保守，用户日后重新引用无需重传。文件名仍被引用着（哪怕解析不到）也不删。
- 白名单 png/jpg/jpeg/gif/webp/pdf 与服务端一字不差；**刻意不含 svg**（能内联脚本，
  浏览器直出等于开一条 XSS 通道）。上限 10MB，本地先挡一道。

### 附件目录配置的统一

M1 把粘贴附件目录放在本机 localStorage、插件放在库内配置，两边换用要设两次——这是
M2 文档里记着的遗留。M3 把它统一到**库内配置的 `pastedImageFolder`**（与插件同一个键）：

- Quick Note 的粘贴链路改为读库内配置；
- 本机那份旧设置不删，但只在打开仓库时作**一次性迁移**（用户真的改过才迁，默认值
  `attachments` 不值得为它写盘——库内读不出这个键时本来就按它兜底）；
- 同步一开，这个键跟着 `quick-daily-note.json` 的补丁式写回分发，多台设备自动一致。

## 十一、范围外与遗留

- **`{{date:}}` 之类的模板与天气、待办提醒**仍属 M4；`todoReminderTime` 等键只保证不被抹掉。
- **没有单文件排除 / 暂停同步**：要停只能关掉自动同步开关。
- **同步不写日志文件**，只有状态栏与横幅；排查线上问题要去后端看。
- **单条内容 > 1MB 会被跳过并提示**（服务端限制），长笔记不会被截断上传。
- **`.MD` 大写后缀的笔记不同步**：服务端的扩展名白名单是 `endsWith(".md")`，
  推上去会让整批 400。与插件一致，宁可少同步一个文件也不让整批失败。
- **不是合法 UTF-8 的文件不同步**：Obsidian 读这种文件会把非法字节替换成 U+FFFD 再推上去
  （等于把文件改坏），我们跳过并在界面上说明。
- **附件之外的库内文件（非 `.md`）不参与正文同步**，与插件的 `scope` 语义一致。
- **没有"单张附件排除"**：不想同步某张图，唯一的办法是取消引用。
- **粘贴即传（0.2.0 修复）**：附件路径也走文件监听入队（曾经只排 `.md`，贴图要等下一轮
  全量扫描才上云，网页端在那几分钟里看到的是裂图）。"取回通道"的分工要说清楚：拉取流的
  附件元数据（`path=` 寻址）与按名补下（`name=` 寻址）是**两条并行的合法通道**，谁先到
  都行——按名通道存在的真正理由是"版本号已被游标越过"的场景，测试用确定性的
  游标外注入来覆盖它，而不是断言"发生过 name= 请求"（那是个时序竞态，两种结果都对）。
- **多实例**：两个 Quick Note 实例同时开同一个仓库会互相覆盖状态文件。目前没有单实例锁。
- **换仓库会重新全量拉取一次**：游标与哈希是"我在**这个**仓库里看到过什么"，换仓库时必须
  归零——带着别的仓库的哈希去比对，同名文件（`日记/2026-09-15.md` 这种在两边都常见）会被
  误判成"本地改过"（多推一遍）或"云端已删"（**误删本地文件**）。切回上一个仓库同样是一次
  全量。状态里记着仓库路径，逻辑在 `adaptStateToVault`，纯逻辑测试里逐条断言。

## 十一、资源占用

同一会话内、同步启用前后各测一次（测试变体，`test-vault`）：

| 状态 | 私有工作集 |
|---|---|
| 同步未配置 | 90.7 MB |
| 同步已启用、空闲（设置面板关闭） | 93.9 MB |

**怎么读这个数字**：差值约 **3 MB**，落在噪声量级——同步的常驻开销只有几个定时器、
一张哈希表与一个引擎对象；大头仍然在 WebView2。**不要**拿它去和 M1/M2 文档里的数字
横向比，那几组是不同工作负载下测的。真正的内存开销发生在同步进行中（扫描整库 + 解析
JSON 响应），而那是瞬时的，且已被 M1 的"不把全库元数据放进渲染进程"这条约束限制住：
扫描与哈希在 Rust 侧完成，渲染进程只拿到一张小表。
