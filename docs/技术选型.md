# Quick Note 技术选型

> 目标：替代 Obsidian 的轻量笔记软件。目录即仓库（纯 Markdown 文件），支持富文本编辑，功能向 quick-daily-note 插件对齐，复用已有的 daily-sync 同步服务。
>
> 调研时间：2026-09-14 ｜ M0 实现情况见 [M0-实现说明.md](M0-实现说明.md)

---

## 一、结论（TL;DR）

| 层 | 选型 | 理由一句话 |
|---|---|---|
| 应用外壳 | **Tauri v2**（2.11.x，Rust + 系统 WebView） | 安装包小、原生文件监听/托盘/通知齐全、MIT/Apache 生态，重活交给 Rust |
| 编辑器 | **CodeMirror 6 + Live Preview 装饰层** | 缓冲区本身就是 Markdown 字节，保存无损；这正是 Obsidian 自己的实现方式 |
| 仓库模型 | 文件夹即 vault，vault 名 + 相对路径为标识 | 与现有 daily-sync 协议 1:1 对齐，可与 Obsidian 插件同时同步同一仓库 |
| 衍生索引 | SQLite（FTS5）作为**可重建缓存**，永不作为数据源 | 日历/字数/搜索走缓存，Markdown 文件永远是唯一真相 |
| 不做 | **不 fork 任何现成笔记应用** | 主流候选要么 AGPL/GPL 传染，要么是 DB-first 存储模型，功能仍要全部自己写 |

**必须先纠正的前提**（详见第二节）：在 Windows 上，Tauri **并不比 Electron 省内存**。真正把内存从 Obsidian 的 400MB~1GB+ 降到 100~200MB 的，是**架构**（单 webview、懒加载、索引不进渲染进程、不加载插件动物园），而不是换了外壳。

## 二、关键纠正：Windows 上的内存真相

这是本次调研最重要的发现，直接影响选型逻辑，必须先摆出来。

Tauri 在 Windows 上用的是 **WebView2**，它和 Electron 一样是 Chromium 内核。所以"Electron 重、Tauri 轻"这个说法在 **Windows 上基本不成立**，只在 Linux（WebKitGTK）和磁盘占用上成立。

唯一可查的跨框架基准（Elanis/web-to-desktop-framework-comparison，MIT，2025-05 的数据，经 HN 引用）单窗口 release 构建空闲 RSS：

| 框架 | Windows x64 | macOS arm64 | Linux x64 |
|---|---|---|---|
| Tauri | **≈154 MB** | ≈86 MB | **≈16 MB** |
| Electron | **≈93 MB** | ≈121 MB | ≈70 MB |
| Wails | ≈163 MB | ≈85 MB | ≈86 MB |
| Neutralino | ≈282 MB | ≈109 MB | ≈402 MB |

**怎么读这组数字（重要）：**
- 单一来源、数据停在 2025-05，不能当定论。RSS 会重复计算 Chromium 共享页，Tauri 的 WebView2 浏览器/GPU 进程与 Edge 硬链接共享，度量口径对 Tauri 不利。
- 但方向可信：**Windows 上带 webview 的桌面应用，地板就是 Chromium 级，约 90~160MB**。Tauri 不会给你"几十 MB"。
- Tauri 真正确定赢的地方：**安装包/磁盘占用小约 10 倍**（实测应用约 3~15MB vs Electron 约 85~200MB）、Linux 内存、以及不捆绑运行时。

**推论**：如果"内存"是唯一硬指标，只有**不用 webview 的原生 UI**才能到几十 MB（egui/Slint/Qt）。但原生 GUI 做不了 Markdown 富文本编辑（表格、图片、Mermaid、代码高亮、HTML 透传），代价远大于收益，**不推荐**。

所以本项目的目标应定为：**从 Obsidian 的 400MB~1GB+ 降到 100~200MB**，并且把"降内存"落在架构上。这个目标现实、可验证，也比"几十 MB"的口号更可信。

> Obsidian 的实际占用我在调研阶段无法从可信来源核实，上面按你的实际感受描述。**M0 已在本机实测**，结论需要修正，见下。

### M0 实测修正（本机，2026-09-14）

测同一时刻的两者，三个口径结论互相矛盾：

| 指标 | Quick Note | Obsidian | 谁更省 |
|---|---|---|---|
| 工作集合计 (WorkingSet) | 408.3 MB | 211.1 MB | Obsidian |
| 私有提交合计 (PrivateBytes) | 148.5 MB | 696.9 MB | Quick Note（4.7×） |
| **私有工作集合计 (PrivateWS)** | **99.5 MB** | **145.9 MB** | **Quick Note（约省 32%）** |

工作集重复计算 Chromium 共享页，私有提交包含已换出到页面文件的部分，两者都不适合跨应用对比；**私有工作集**最接近"实际吃掉多少内存"。

**所以要修正本文原先的预期**：我此前说"Obsidian 用 400MB~1GB+"、目标是"降到 100~200MB"。实测 Obsidian 在本机的物理占用只有约 **146MB**，Quick Note 约 **99.5MB**——**优势是约三分之一，不是数倍**。Quick Note 落在预估区间的好一端，但"降到十分之一"这种预期不成立。

另外，Rust 主进程私有内存只有 **5.5MB**，其余全部来自 WebView2 进程。这实测印证了第二节的判断：**地板由 Chromium 内核决定，省内存只能靠架构**。

这是一次非受控对比（Quick Note 刚启动、一篇小笔记；Obsidian 运行较久、3 个仓库、带插件）。要得到可靠结论，需两者都冷启动并打开同样内容后再测——详见 [M0-实现说明.md](M0-实现说明.md)。

## 三、为什么不 fork 现成的开源笔记应用

"选一个开源的底座"有两种理解：fork 一个现成笔记应用，或选一个底层框架。调研后明确结论：**应该选框架，不应该 fork 应用。**

### 3.1 许可证会传染

| 应用 | 许可 | 影响 |
|---|---|---|
| Joplin | AGPL-3.0-or-later | 网络条款：分发即需开源，且 LICENSE 声明 Joplin® 商标 |
| Logseq | AGPL-3.0 | 同上；且上游 DB 版在 beta，"可能数据丢失" |
| SiYuan | AGPL-3.0 | 同上 |
| Trilium / TriliumNext | AGPL-3.0 | 同上 |
| AppFlowy | AGPL-3.0 | 同上 |
| MarkFlowy | AGPL-3.0 | 同上（Tauri + ProseMirror，技术很合，但许可挡路） |
| Notesnook / Zettlr | GPL-3.0 | 分发需开源 |
| QOwnNotes / MindForger | GPL-2.0 | 同上 |
| VNote | LGPL-3.0 | 相对宽松，但仍有限制 |
| **Anytype** | "Any Source Available License 1.0" | **根本不是开源** |
| AFFiNE | 多数 MIT，backend 例外 | 存储模型不符 |
| MarkText / SilverBullet / Foam | MIT | 许可可用，但见下 |

### 3.2 存储模型不符（更致命）

你的硬约束是"**纯 .md 文件夹即真相**"，并且同步协议以 **文件路径 + 内容 SHA-256 哈希**为增量判断依据。以下全部把 Markdown 降级成导入/导出格式，真相在私有数据库里：Joplin（SQLite）、SiYuan（`.sy` JSON + SQLite）、Trilium（自有 DB）、Notesnook（加密 DB）、Anytype / AppFlowy / AFFiNE（自有对象存储 / Yjs）。

### 3.3 功能省不下来

你的功能清单（按日期建日记、ISO 周记、日历侧栏 + 每日待办、模板占位符、周回顾、待办顺延、粘贴识别语言、图片粘贴 + 附件目录、图片工具栏、Mermaid 增强、全局背景、定时提醒、天气）**全是应用级功能**。小体量 Tauri 应用没有插件 API，fork 完这些照样要自己写。fork 能省下的只有外壳和编辑器接线——恰好是最便宜的部分。

### 3.4 可借鉴的 MIT 项目（**借鉴，不是 fork**）

| 项目 | 技术 | 可借鉴点 |
|---|---|---|
| `kenforthewin/atomic-editor` | MIT，CodeMirror 6 | **最有价值**：Obsidian 式行内 Live Preview 的完整参考实现，含表格/图片/复选框 widget，宣称"导出字节与纯 textarea 完全一致" |
| `zhitongblog/solomd` | MIT，Tauri 2 + Vue 3 + CM6 | 文件夹即仓库 + Typora 式即时渲染 + Mermaid/KaTeX，功能最接近；但仅 1k stars、macOS 优先 |
| `mattenarle10/markamd` | MIT，Tauri 2.11 | 干净的 Tauri 笔记骨架 |
| `silverbulletmd/silverbullet` | MIT | 纯 md 落盘 + 即时预览的模型参考；但它是 Deno 服务端 + 浏览器，不是桌面应用 |

## 四、推荐架构

```
┌─────────────────────────────────────────────────────────┐
│ Tauri v2 外壳（Rust）                                    │
│  · 窗口/托盘/全局快捷键/通知/自启/自动更新                │
│                                                          │
│  ┌────────────────────────┐   ┌──────────────────────┐  │
│  │ Rust Core（后台）       │   │ WebView（单个）       │  │
│  │ · vault 文件读写/监听   │◄─►│ React 19 + TS        │  │
│  │ · SQLite FTS5 索引缓存  │IPC│ · CodeMirror 6       │  │
│  │   (由 md 重建，非真相)  │   │   Live Preview 编辑器 │  │
│  │ · 同步客户端(JWT+push/  │   │ · 日历/待办/周记面板   │  │
│  │   pull) + 冲突处理      │   │ · 设置/背景/模板       │  │
│  │ · 定时提醒/天气抓取     │   │ · 懒加载 Mermaid/KaTeX │  │
│  └────────────────────────┘   └──────────────────────┘  │
└─────────────────────────────────────────────────────────┘
              │ HTTPS (JWT + JSON)
              ▼
      现有 daily-sync 后端（Spring Boot + MySQL）
```

**职责划分原则**：渲染进程只持有**当前打开的文档 + 当前视图数据**；全库扫描、索引、同步、HTTP 全部在 Rust 侧。这是与 Obsidian 最大的架构差异（Obsidian 把全库元数据缓存放在渲染进程里）。

## 五、编辑器选型：为什么是 CodeMirror 6

### 5.1 决定性论据：同步协议用内容哈希判增量

你的 daily-sync 协议靠 `SHA-256(content)` 对比决定"是否变化"，且冲突解决是"本地改动胜出 + 回推 dirty"。这意味着：

> **编辑器在保存时重写用户没动过的 Markdown（改列表符号、重排换行、转义、丢 HTML），会直接制造虚假改动与虚假冲突，把同步搅乱。**

CM6 Live Preview 的缓冲区**就是** `.md` 原文，保存即写回，天然字节无损。这一条几乎单独决定了选型。M0 已实测验证：见 [M0-实现说明.md](M0-实现说明.md) 中的两个陷阱与验收脚本。

### 5.2 候选对比

| 引擎 | 许可 | Markdown 模型 | 往返保真 | 性能/内存 |
|---|---|---|---|---|
| **CodeMirror 6**（推荐） | MIT | 文档即 md 文本 | **字节精确** | 视口虚拟化 + lezer 增量解析，**最佳** |
| Milkdown 7.x | MIT | ProseMirror + remark | 语义级，**会规范化**标记/换行 | 无虚拟化，长文可能卡 |
| TipTap 3.x | MIT（Pro 除外） | ProseMirror + marked | 取决于每个扩展的解析/序列化规则 | 中等 |
| Lexical | MIT | Transformer | `normalizeMarkdown()` 会重写 | 中等，无原生 HTML 节点 |
| BlockNote | MPL-2.0，`xl-*` 为 GPL/商业 | 块 → HTML → Markdown | **本质有损** | 重 |

补充事实：
- CodeMirror 与 ProseMirror 已于 2026-04 迁出 GitHub，主仓库在 `code.haverbeke.berlin`，npm 发版节奏不变。
- Wordgard 0.1（Haverbeke 的新项目，2026-07）**尚无 Markdown 支持**，且明说至少一年停在 0.x，**观察，不采用**。
- 所有引擎都**没有**成熟的 Mermaid 集成（`tiptap-extension-mermaid`/`prosemirror-mermaid` 都停在 `0.0.0`），Mermaid 必须自己接：解析围栏块 → `mermaid.render()` → 作为 widget 注入。

### 5.3 关于"富文本编辑"的取舍

Obsidian 的 Live Preview 在观感上就是富文本，只是语法标记在光标移开时被装饰隐藏。建议照抄这个三模式设计：

- **Live Preview**（默认，CM6 + 装饰层）：满足"富文本编辑"体验，且字节无损。
- **源码模式**：同一缓冲区，去装饰。
- **阅读视图**：只渲染。

若你坚持要 Notion 式**真·块级 WYSIWYG**，退路是 **Milkdown Crepe**（MIT，自带 KaTeX + CodeMirror 代码块 + GFM 表格/任务列表 + DOMPurify），代价是 remark 会规范化用户手写的 Markdown、且无虚拟化。**这个取舍建议现在定下来**，因为编辑器下面的所有功能都挂在它上面。

## 六、与现有 daily-sync 的对接（可直接复用，无需改后端）

调研已确认的协议事实：

- 鉴权：`POST /api/v1/auth/login` 取 JWT（access 2h / refresh 30 天，refresh 一次性轮换）。`Authorization: Bearer`。
- 推送：`POST /api/v1/sync?vault=<name>`，body `{items:[{path,content}]}` 或 `{path,deleted:true}`；单批 ≤200；响应 `{vaultVersion, results:[{path,status}]}`。
- 拉取：`GET /api/v1/sync?vault=&since=&limit=500`；游标是 **vault 版本号**（不是时间戳），`limit` 上限 500，`hasMore` 时用 `since = 末条version - 1` 再取并去重。
- 约束：path ≤255 字符、相对路径、无 `\`、无 `.`/`..`、必须以 `.md` 或 `.json` 结尾；content ≤1,048,576 字符。
- **vault 名就是 Obsidian 的 `app.vault.getName()`**，`(user_id, name)` 唯一，服务端隐式创建。
- 两个特殊文件是普通记录：`quick-daily-note.json`（插件配置 + 待办）与 `daily-sync-todos.json`（待办快照）。

**因此，QuickNote 的设计目标是"与 Obsidian 插件同仓库共存，且同步不打架"：**

1. **仓库名可显式设置**，默认取文件夹名，允许用户改成与 Obsidian 库同名的值 → 映射到服务端同一个 vault。
2. **读写同一份 `quick-daily-note.json`**，格式与插件保持一致（含 `{{title}}/{{date}}/{{week}}` 模板配置、日记目录、日期格式）。这样两边换用无需重新配置。→ **M2 已落地**：目录、日期格式、两个模板与待办数据都与插件共用同一份文件，且是**补丁式写回**（只改自己管的 8 个键，其余原样保留）。
3. **待办快照沿用 `daily-sync-todos.json`**，合并语义照抄 `todos.ts`：按 `id` 条目级合并、`updatedAt` 新者胜、墓碑保留 30 天。→ **M2 备好了数据模型，M3 已落地快照与合并**（虚拟文件，不落盘；合并结果会回推，让第三台设备也拿到）。
4. **同步客户端逻辑直接移植 `sync.ts`**：它是纯 TypeScript，只需把 Obsidian 的 `requestUrl` 换成 `fetch`、`app.vault` 换成 Rust 侧的文件命令。冲突策略原样保留（本地改动胜出 + 回推 dirty）。
5. **后台化**：push 防抖 3s、周期 5min、启动后首次 5s——这些常量照搬，保持两边行为一致。

## 七、其他候选为什么不选

| 候选 | 否决理由 |
|---|---|
| Electron | Windows 上内存并不更差（基准里反而更低），但安装包大 10 倍、磁盘占用重；且我们要的是"架构省内存"，Tauri 的原生能力更划算。**注**：webview UI 代码可平移到 Electron，所以选 Tauri 是低后悔决策 |
| Wails v3 | 2026-09 仍是 beta（beta.21 每日构建），无稳定时间表，插件生态几乎为零（`topic:wails-plugin` 零结果）。v2 稳定但相对 Tauri 无优势 |
| Neutralinojs | 唯一可用基准里**最重**（Win ≈282MB / Linux ≈402MB），与"轻量"宣传矛盾 |
| Sciter / Ultralight | 私有许可（Ultralight 的"轻 10 倍"是无方法论的市场宣传），富文本工具链弱 |
| Servo / Verso | Tauri 的 Servo 后端官方自述"仍在积极开发，尚不如生产后端功能丰富"，2026 不可用于交付 |
| VS Code 系（Foam / Dendron） | VS Code 本身就是 Electron，issue 里有 7GB+ 的报告；Dendron 2025-11 后无提交。**不比 Obsidian 轻** |
| QOwnNotes / VNote | 真正原生低内存（C++/Qt，纯 md 文件夹），但无 WYSIWYG、C++/Qt 迭代慢、GPL-2.0/LGPL 传染 |
| Logseq | 44.9k stars 但 AGPL-3.0 + Electron + ClojureScript，内存问题是长期未解的公开 issue，且上游正迁向 DB 存储 |
| SilverBullet 式"本地服务 + 浏览器" | 边际内存极低（复用已开浏览器的一个标签页），但要常驻服务、无托盘/全局快捷键，不像"软件"。若内存是绝对第一优先级，可作为备选形态 |

## 八、把内存真正压下来的清单

外壳只决定地板，天花板靠这些：

1. **只有一个 webview**，不要为每个笔记开窗口/多 webview。
2. **不把全库元数据放进渲染进程**——日历、字数、搜索、反向链接全部走 Rust + SQLite 查询接口，只回传当前视图需要的数据。
3. **懒加载重依赖**：Mermaid（12.x，体积大）、KaTeX、语法高亮语言包，全部按需 `import()`，只在文档里真的出现该围栏块时加载，且**缓存上限 + 卸载**。M0 已验证 CodeMirror 的语言包会自动切成独立 chunk。
4. **`backgroundThrottling`**：窗口不可见时 `throttle`/`suspend` 渲染进程。
5. **文档不常驻**：切换笔记时释放编辑器 state（保持 LRU 上限，如 3 篇）。
6. **不用 DOM 渲染长文档**：CM6 视口虚拟化天然满足；阅读视图也要虚拟化。
7. **图片不整图进内存**：大图走缩略图 + 按需解码，背景图/视频尤其注意（插件的视频动态壁纸是内存杀手，建议默认关闭并在设置里明确警告）。
8. **文件监听用 Rust `notify` 并做防抖**，不要在前端轮询扫描目录。
9. **索引是缓存**：SQLite 文件可随时删除重建，启动时校验 mtime/哈希，避免全量重扫。
10. **不实现插件系统**（第一版）。Obsidian 的内存崩溃很大比例来自插件；内置功能按需加载即可。

验收方式：与第二节记录的 Obsidian 实测基线对比，并把"空闲 RSS""打开 10MB 文档后的 RSS""切换 20 篇笔记后的 RSS"作为回归指标。

## 九、分阶段落地

**M0 外壳验证（先做，1~2 天）**
建 Tauri v2 + React + CM6 最小应用：打开文件夹、列出 `.md`、编辑一篇、保存字节一致。**在此阶段就实测 Windows 空闲 RSS**——如果与预期差距过大，此时切换到 Electron 的成本几乎为零。→ **已完成，见 [M0-实现说明.md](M0-实现说明.md)**

**M1 仓库与编辑器**
vault 抽象（文件夹 = vault，可配置 vault 名）、文件树、CM6 Live Preview 装饰层（标题/粗斜体/行内代码/链接/复选框/图片/表格）、附件目录与图片粘贴、三模式切换、文件监听与外部改动提示。参考 atomic-editor。

**M2 日记与日历（已完成，见 [M2-实现说明.md](M2-实现说明.md)）**
按日期建日记（日期格式可配、存放目录可配）、标题规则"日期 + 名字"、同名直接打开、同一天多篇、ISO 周记（`2026-W37 周记`）、模板与 `{{title}}/{{date}}/{{time}}/{{week}}/{{date:格式}}` 占位符、日历面板（含 W 周记列、圆点标记、双击创建）、本月天数/连续天数/今日字数、待办录入与勾选、昨日未完成顺延。

落地时明确的两条：**库内 `quick-daily-note.json` 采用补丁式写回**（插件专有键与键序原样保留，解析失败则拒绝写回），**日期格式用 moment 解释**（与插件共用同一个引擎，ISO 周号跨年才不会错格）。待办的合并与快照已在 M3 落地。

**M3 同步（已完成，见 [M3-实现说明.md](M3-实现说明.md)）**
移植 `sync.ts` → Rust 同步模块 + 前端调度；vault 名映射；游标/`hasMore`/去重、哈希比对、dirty 回推、冲突提示；`quick-daily-note.json` 与 `daily-sync-todos.json` 兼容；后台防抖/周期同步。**开工前先解决第十一节列出的哈希口径问题。**

落地时明确的三条：
- **哈希口径已核实**（阻断项解除）：Obsidian 的 `Vault.prototype.read` 是 `fs.readFile(utf8)` 后剥掉开头的 U+FEFF，换行符不做规范化。所以同步哈希取"**已剥 BOM 的正文**"，磁盘上的 BOM 依旧原样保留（BOM 只是不参与哈希与上传）。插件 `data.json` 里 9 个文件的哈希逐条复核一致。
- **HTTP 走 Rust 而不是渲染进程的 `fetch`**：后端没有 CORS 响应头，WebView 的源发不出去；而且账号密码与 JWT 不该放在页面脚本能直接读到的地方。
- **附件同步留到下一步**（M3 的已知缺口）：它的前提是附件目录配置两边统一（Quick Note 放在本机设置、插件放在库内配置）。但**游标已经把附件的版本号一起吃掉**，将来接上不会漏。

**M5 打包与体验**

移植红利：插件里的 `languageDetect.ts`、`todos.ts`、`sync.ts` 与大量 UI 逻辑都是纯 TypeScript，**可大面积直接复用**，这是不 fork 现成应用、改为"Tauri + 复用自有插件代码"的最大优势。

## 十一、风险与未核实项

> M0 的实现约束、实测发现的两个 CodeMirror 陷阱与验证方案，见 [M0-实现说明.md](M0-实现说明.md)。

- ~~**内容哈希的跨客户端口径（M3 阻断项，优先级最高）**~~ **已核实并落地（M3）**：本项目对文件内容哈希取的是**原始字节**（含 BOM、CRLF 原样），而 Obsidian 插件侧的 `sync.ts` 是经 vault API 读成文本再哈希的。**核实结果**：Obsidian 的 `Vault.prototype.read` 是 `fs.readFile(path, "utf8")` 后剥掉开头的 U+FEFF（`65279 === charCodeAt(0)`），**换行符不做任何规范化**。于是同步口径定为"**已剥 BOM 的正文 UTF-8 字节**"，磁盘上的 BOM 原样保留、写回仍是字节精确的；已用插件 `data.json` 里 9 个文件的哈希逐条复核。详见 [M3-实现说明.md](M3-实现说明.md) 第一节。
- **内存数字**：唯一跨框架基准数据停在 2025-05，且 RSS 口径对 Tauri 不利；Obsidian 实测值未核实。**必须自测**，不要基于本文数字做承诺。
- **CM6 Live Preview 的工程量**：装饰层的"光标所在行显示源码"这类边界（选区、IME、最短行回退）是 bug 高发区，需预留时间；atomic-editor 可作起点但仍要自建表格/Mermaid/KaTeX widget。
- **Mermaid/KaTeX 无成熟现成集成**，需自研 widget 并在懒加载 + 卸载上做好内存管理。
- **开源项目活跃度**随日期变化，solomd/markamd 等新项目体量小、可能需要先读源码确认其 vault 抽象能否挂同步。
- **WebView2 依赖**：Windows 11 内置、Win10 绝大多数已装；离线安装需 +127MB 装包或走 Evergreen 引导（~2MB，需联网）。
- **文件监听已实现（M1）**：Rust `notify` 递归监听 + 250ms 去抖，前端按哈希区分「自己写入的回声」与真外部改动；有未保存编辑时弹冲突提示，不静默覆盖。
- **工具链与网络环境（实测）**：本机 rustc 1.87 无法构建——Tauri 的部分依赖（`time`、`plist`、`serde_with`、`icu_provider`）要求 1.88+。已升级至 1.98.1。另外从官方 CDN 拉工具链在本机只有约 55 KB/s（约需 1 小时），换清华 TUNA 镜像（`RUSTUP_DIST_SERVER=https://mirrors.tuna.tsinghua.edu.cn/rustup`）后约 40 秒完成——**换机或重装环境务必先设镜像**。
