# M5 预览内存优化实现说明

> 目标：在 0.6.0 已完成的"预览内存治理"（worker 单例/关闭即 terminate/图表孤儿回收/响应式）之上，
> 把占用再往下压。预期合计 **−50~90MB**：空闲/轻编辑逼近 150–170MB（release 私有工作集口径），
> 预览会话峰值再降 40–80MB。

## 0. 验收口径（先读这节，否则数字全失真）

1. **只用 release exe 测**：dev 窗口（vite + StrictMode + 未压缩 + sourcemap）虚高 30–50%。
2. **用私有工作集**（`scripts/measure-rss.ps1` 的 PrivateWS），任务管理器的"工作集/组合计"含共享代码页，严重偏高。
3. **关闭预览后等 2 分钟再读数**（V8 惰性归还 + 我们的闲置回收都是延迟的）。
4. 判断标准是**连续开关预览 10+ 次后是否单调上涨**（不涨 = 无泄漏），而不是"是否回到首次空闲值"——
   按需加载的渲染器模块代码（pdfjs/docx-preview/pptx+echarts）一旦加载**无法卸载**，是常驻底数。

**天花板认知**：WebView2 运行时底座（浏览器主进程+GPU+网络服务）100–150MB + 编辑器核心
（CodeMirror/React/DOM）~120MB，这两块任何方案都减不掉。本方案动的是模块底数与峰值。

## 改动一：PDF 页 canvas→JPEG + 渲染取消 + doc.cleanup()

**收益**：滚动尖峰 −10~20MB；翻回已看页秒开（0.3MB/页缓存）；长会话 worker 内缓存回收。
**文件**：`src/components/FilePreview.tsx`（PDF 分支，约 201–325 行）。

1. **img 缓存替代 canvas 常驻**：
   - `renderPage` 里 `await pdfPage.render(...).promise` 完成后：
     `canvas.toBlob(blob => { const url = URL.createObjectURL(blob); /* img 替换 canvas */ }, "image/jpeg", 0.85)`
   - `<img>` 宽高样式与 canvas 相同（`width:100%; height:100%`）；随后 `canvas.width = canvas.height = 0` 归还位图。
   - JPEG 无透明通道——PDF 页不透明，无问题；文字页 0.85 质量约 0.3MB，扫描插图页可到 1–1.5MB（可接受）。
2. **缓存表替代 renderedRef**：
   - `imgCacheRef = useRef<Map<number, string>>(new Map())`（页码 → blob URL）。
   - 进入视口：缓存命中直接挂 `<img>`；未命中才渲染。
   - 离开视口：**不再摘除**（这就是翻回秒开的代价与收益）——改为 LRU 淘汰：上限 60 页，超出 revoke 最旧
     （`URL.revokeObjectURL` + Map 删除）。切换文件/卸载时全量 revoke（挂进现有 release 流程）。
3. **渲染任务取消**：`renderTaskRef = useRef<Map<number, RenderTask>>`；`renderPage` 里保存
   `pdfPage.render(...)` 返回的 task；同一页再次触发渲染前先 `task.cancel()`（避免过期渲染白跑，快速滚动明显）。
4. **doc.cleanup() 闲置回收**：预览打开期间，最近一次渲染 60s 后调一次 `docRef.current?.cleanup()`
   （释放 worker 内字体/图案/逐页缓存，滚动时 pdfjs 自动重建）。用 setTimeout 实现，渲染前 clearTimeout。
5. 占位/`aspect-ratio` 响应式逻辑**不变**——只是 slot 里放的东西从 canvas 变成 img。

## 改动二：xlsx 解析 Worker 化

**收益**：SheetJS（~8–15MB 模块底数）不再常驻主线程。
**文件**：新建 `src/lib/xlsxWorker.ts`；`src/components/FilePreview.tsx` spreadsheet 分支。

1. worker 文件（注意：**必须 `?worker&inline` 构造**，tauri 自定义协议下跨源加载 module worker 会静默失败——
   与 pdfjs worker 同款坑，见 FilePreview 头部注释）：
   ```ts
   import * as XLSX from "xlsx";
   self.onmessage = (e: MessageEvent<{ id: number; base64: string }>) => {
     try {
       const bytes = Uint8Array.from(atob(e.data.base64), (c) => c.charCodeAt(0));
       const wb = XLSX.read(bytes, { type: "array" });
       const sheets = wb.SheetNames.map((name) => ({ name, html: XLSX.utils.sheet_to_html(wb.Sheets[name]) }));
       self.postMessage({ id, sheets });
     } catch (err) {
       self.postMessage({ id, error: String(err) });
     }
   };
   ```
2. 主线程封装 `parseXlsxInWorker(base64): Promise<{name,html}[]>`：每次**新建 worker、返回即 terminate**
   （用完即杀，主线程永不留底数；单文件解析 1–2 秒可接受，"正在加载…"遮罩已有）。
3. FilePreview 的 spreadsheet 分支：`readBinary` 返回的 `data.base64` 直接传 worker（别走 base64ToBytes 再转回来）；
   返回后沿用现有 `DOMPurify.sanitize` + sheets state 流程（sanitize 依赖 DOM，留在主线程）。
4. 验收：多 sheet 切换、大表打开、格式错误文件报错路径正常。

## 改动三：mermaid 渲染 Worker 化（最大单点 −30~50MB）

**现状**：`src/lib/livePreview.ts:365` `mermaidLoader = import("mermaid")` —— 打开过含图笔记后整块常驻主线程。
**文件**：新建 `src/lib/mermaidWorker.ts`；改造 `livePreview.ts` 的 mermaid 调用点。

1. worker 文件：
   ```ts
   import mermaid from "mermaid";
   let initialized = "";
   self.onmessage = (e: MessageEvent<{ id: number; code: string; config?: string }>) => {
     const { id, code, config } = e.data;
     if (config && config !== initialized) {
       mermaid.initialize(JSON.parse(config));   // 主题等设置变化时重发
       initialized = config;
     }
     mermaid.render(`m${id}`, code)
       .then(({ svg }) => self.postMessage({ id, svg }))
       .catch((err) => self.postMessage({ id, error: String(err) }));
   };
   ```
2. 主线程封装 `renderMermaidInWorker(code, config): Promise<string>`：
   - worker 单例 + 请求自增 id + pending Map 兑现 Promise；
   - **闲置 terminate**：最近一次渲染 10 分钟后 `worker.terminate()` 并置空单例（下次重建约 1s，可接受；
     不做 terminate 的化 worker isolate 同样常驻，白改）；
   - 主线程用 `import("pdfjs-dist/build/pdf.worker.min.mjs?worker&inline")` 同款方式构造：
     `new Worker(new URL("./mermaidWorker.ts", import.meta.url), { type: "module" })` 若在 tauri 协议下
     加载失败，退回 `?worker&inline`（二选一，先试 URL 版，dev 控制台无跨源报错即成）。
3. **不做主线程回退**：渲染失败就在笔记里显示错误占位——回退会把 mermaid 拉回主线程，前功尽弃。
4. mermaid 的 `initialize` 配置（主题跟随设置）每次渲染时一并传给 worker，保证深浅色切换后图形正确。
5. 验收：打开大 mermaid 笔记——图形渲染正常、切主题后重渲正确、编辑防抖后更新正常；
   私有工作集对比：mermaid 模块 30–50MB 从主线程消失。

## 改动四（可选，观感招）：Windows 空页修剪

**收益**：任务管理器观感立竿见影；**"已提交"内存不降**，纯观感优化。
**文件**：`src-tauri/src/lib.rs`（新增 command）+ 前端预览关闭处调用。

1. Rust 端（Windows only）：
   ```rust
   #[cfg(windows)]
   #[tauri::command]
   fn trim_working_set() {
       use windows_sys::Win32::System::ProcessStatus::EmptyWorkingSet;
       unsafe { EmptyWorkingSet(GetCurrentProcess()); }
   }
   ```
   （依赖 `windows-sys` crate 的 `Win32_System_ProcessStatus` + `Win32_System_Threading` feature；非 Windows 提供空实现。）
2. 前端：`FilePreview` 的卸载清理里（或窗口最小化事件）`invoke("trim_working_set")`。
3. 诚实标注：这是让数字好看，不是真省内存；页面被裁出工作集后首次访问会有轻微缺页开销。

## 执行顺序与时间预算（晚间 ~2h）

1. 改动一（30min，最独立、收益确定）→ `npm run build` + tauri build → release 实测 PDF 滚动/翻回。
2. 改动二（30min）→ 验收 xlsx。
3. 改动三（45–60min，动 livePreview 渲染管线，留整块时间）→ 重点回归：含图笔记渲染/主题切换。
4. 改动四（15min，可选）。
5. 每步之后用 measure-rss.ps1 记一个数：空闲 / 打开 PDF / 打开含图笔记 / 连续开关 10 次后。
